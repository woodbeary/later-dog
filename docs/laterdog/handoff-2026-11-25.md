# Handoff, 2026-11-25: the refinement program

Written for whoever continues this from later.dog Dev. It says what the program is, what exists, what is proven,
what is not, and what to do next, package by package. The tracker is the "Refinement program" section of
[finish-line.md](finish-line.md); this file is the long form.

## What this is

One pass over the desktop and the phone for speed, weight and fewer surfaces that say the same thing. The owner's
words for both apps were twitchy, sluggish and redundant. The method: measure first, change one thing per pull
request, show the number before and after from the same script on the same machine, and let a budget check stop
anything getting worse.

Decisions already made, not to be reopened without the owner:

1. **A reply arrives finished on both apps.** The desktop always worked this way
   ([chat-ui.md](../verification/chat-ui.md), "In-flight reply text"). The phone now does too (package B6).
   Until a reply lands, the person sees the dog working, so that wait is the main experience and track E designs it.
2. **No Rust component and no new shell** unless a step still misses its budget after tracks B to D and a
   JavaScript fix (a worker first) cannot close it: the bar set in [rust-seams.md](../verification/rust-seams.md).
   That file's Mac measurements are still owed (track F). One clean-sheet native build of the chat screen may be
   measured beside ours, outside this repository, for a later decision; nothing is rewritten on the strength of it.
3. **Hosted checks return** on GitHub's standard runners for this public repository, with no paid runners.
   Signing, notarizing, releases and device checks stay on the owner's Mac. `pnpm gate` stays the merge rule until
   package G9 moves it.
4. **pnpm stays.** Warm installs take 3 to 11 s and `allowBuilds`, three standalone lockfiles and
   `scripts/pnpm-builds.test.ts` depend on it. **No formatter yet**: a first format would touch about 3,000 files
   across every open branch. **TypeScript 7** for typecheck only after its diagnostics are compared side by side
   with today's compiler.

## First numbers

**Hosted checks before they were removed** ([record](../verification/hosted-checks-audit-2026-11-25.md)). 150 runs,
all on Linux. Waiting 3 s at the median and 6 s at p95; setup 18 s and 26 s; running 169 s and 965 s. Running was
94.8% of all job time. A run took 16.6 minutes at the median because the four test shards each took 14 to 16
minutes with files one at a time. Five files are 29% of the per-file time; `server/delta-context.e2e.test.ts`
takes 269 s alone. Of the 150 runs, 84 passed, 51 failed, 15 were cancelled.

**Desktop launch** ([record](../verification/launch-timeline-2026-11-25.md)). Linux, virtual display, unpackaged,
12 launches of each kind. First launch: 1,830 ms from spawn to a usable message box, of which about 1,060 ms is
the second splash's hold and fade (it left within 12 ms of its 700 ms floor in every run). Repeat launch: 829 ms;
the second splash is already skipped. The window is not created until the whole startup chain has finished, which
in the packaged app includes starting the server and waiting for it to answer; a stand-in for that start took 0.7
to 1.2 s. So the everyday cost is the order of the chain, and the splash is a first-impression cost.

**Desktop while a dog works** ([record](../verification/desktop-performance.md)). A working turn makes 26 commits
and redraws 5,018 components. About 4,750 of those are in ten commits of about 475 components each that land 150
to 400 ms after a recognised frame or key press, so no named cause explains them yet. With Settings open, 22 of 22
frames in the working turn take over 25 ms and the worst takes 83 ms. Four other dogs working: 45 commits, 770
components. A finished reply lands with no task over 50 ms (longest 13.6 to 18.9 ms), so parsing a reply by block
is not needed.

**Landing movement, with a correction.** A1's own three runs saw the rows of a person reading older messages move
48 px, and 103.5 px above when following. Thirteen later runs on two other machines, with both versions of the
script, saw 0 px when reading older messages and 55.5 px when following with the 120-row transcript full, which is
the one row dropped from the top. The 48 px is unexplained and not counted. If it shows on the Mac, it is real.

**Phone.** The bundle is 8,050,741 bytes against a budget of 8,091,648. The only device record is still
[phone-chat-performance-2026-11-10.md](../verification/phone-chat-performance-2026-11-10.md): 37 renders per chat
switch and stalls up to 1,710 ms, against targets of under 5 and 200 ms.

## Things to know before trusting any of it

- **One budget line was loosened.** "Typing, no dog working, frames over 25 ms" went from 0 to 2 after one slow
  run measured 1. It counts slow frames on a shared machine. Put it back to 0 once it is measured on the Mac.
- **Run Check on the phone now sends a message.** The answering pass posts one short line to the first chat unless
  that dog is already working, and the check takes about three minutes. The screen says so.
- **The home does not take the phone's new report yet.** `server/laterdog/phone-perf.ts` validates strictly and
  caps passes at 2. The phone posts the old shape while `PERF_SERVER_TAKES_V2` is false. See package A5 below.
- **B6 removed seven tests** with the feature they covered (3,541 before, 3,534 after). Nobody has gone through
  them one by one.
- **Release builds of the phone import from `src/dev`** in `use-chat-frame`, `MessageBoxCheck`, `Composer`,
  `use-rewind`, `new-dog`, `search`, `new-chat`, `chat/[botId]` and `computer/[botId]`. Only the probe is gated.
- **One desktop test fails only as root in a container**: `move-to-applications`, "read-only folder". Run the gate
  as an ordinary user.

## How to run a package

1. One package, one branch `refine/<id>-<slug>`, one draft pull request. Stack on an unmerged branch only when
   the package needs its code, and say so in the pull request.
2. Node 24 and a frozen install. On a fresh cloud computer: unpack Node 24.6.0 and run
   `pnpm install --frozen-lockfile` (about 11 s warm). On the phone, the repository's `.npmrc` points the store at
   the owner's drive, so a cloud install needs `npm_config_store_dir` and `npm_config_cache_dir` set elsewhere.
3. Take the number first: `node --experimental-strip-types scripts/desktop-perf.ts --budget` after
   `pnpm exec vite build` (134 to 138 s; `--budget-quick` is about 90 s and skips the nine timed lines);
   `node scripts/launch-timeline.mjs --runs 12`; on the phone `pnpm verify` and Run Check.
4. Make the change, take the number again, and lower the line in `scripts/desktop-perf.budget.json` in the same
   pull request. A test stops any line going back up once it is on main.
5. Run the focused tests, `pnpm lint`, `pnpm typecheck`, the no-comments and own-names tests. Say in the pull
   request what has not run.
6. One session keeps the tracker. Other packages do not edit `finish-line.md`.
7. `server/` and `electron/` changes reach the owner's Dev app only after Restart later.dog Dev.

## What to do next

Each entry: the goal, where to look, the number that should move, and what guards it. "Judgment" means give it to
the strongest model; "mechanical" means a lighter one is enough; "design" means the owner sees it before it is built.

### Desktop

- **B2 Name and cut the ten large redraws.** Judgment. Use `--names` with an unminified build and
  `--store-changes` to say what the ten commits of about 475 components are. Suspects: `OpenDog` selecting the
  whole dog (`src/App.tsx` near line 50; `currentTaskBot` spreads a new object in `src/state/store.tsx` near
  397), the eight thread-wide memos in `src/components/ChatView.tsx` near 931 to 979, and native runs read in the
  message list (`ChatView.tsx` near 725) rather than in the work row. Moves: working turn components 5,020 toward
  45. Guard: `ChatView.rows.test.ts`. Stale props were the two regressions of the earlier store branch.
- **B8 Settings panels off the whole store.** Mechanical after B2. About 42 files call `useStore()`; migrate them
  to `useStoreSelector` in batches by folder behind a ratchet test that counts call sites. Moves: Settings open
  components 5,330 toward 45 and frames over 25 ms from 27 toward 0.
- **B1 Stop receiving reply text the window never shows.** Judgment, small. A client that opens the event stream
  with `watch=1` gets an empty watch set and the server withholds `content.delta` for threads not in it
  (`server/stream-watch.ts`); the phone already relies on this. The desktop reads reasoning summaries from the
  same deltas (`src/lib/turn-reasoning.ts`), so decide from the E1 design whether it watches the open thread or
  none. Moves: four other dogs working, 51 commits and 850 components. Guard: `live-frames.test.ts`.
- **B3 One store commit per display frame for network frames.** Judgment. `handleFrame` in `store.tsx` near 3371
  dispatches per frame. Risks: `stateRef.current` is read straight after a dispatch near 3345, and a hidden window
  gets no animation frames. Guards: `live-frames`, `send-delivery` and `queued-steer` tests.
- **C1 Create the window while the server starts.** Judgment. `electron/main.mjs` awaits the native splash,
  credentials, config, server start with its health poll, supervisor and restore before `createWindow`. Creating
  the window and its renderer depends on none of it; only the address it loads does. `await startupScreen.ready`
  holds the chain 81 to 100 ms and nothing after it uses the splash. Moves: app ready to window, and total to
  message box, in `scripts/launch-timeline.mjs`. Needs the packaged Mac app to be believed.
- **C2 One splash.** Design, then mechanical. `src/components/LaunchSplash.tsx` holds 700 ms and fades 360 ms on a
  first launch only. Whether a first launch keeps a moment of brand is the owner's call.
- **C3 Load heavy panels after first paint.** Mechanical. `src/App.tsx` imports the plugins panel (1,125 lines,
  shown only when opened), the command palette, the call host and all of the markdown and maths code up front;
  `vite.config.ts` has no build section. Record the first load's size and budget it.
- **D1, D2, D3.** Typing with a dog working (`--one-dog-streams` is not in the default run, so add its budget line
  first); scroll only if slow frames remain; idle work (an animation loop per avatar in `CursorAvatar.tsx`, a one
  second presence clock, and the polling timers listed in the desktop performance record).

### Hosted checks

Read [hosted-checks-audit-2026-11-25.md](../verification/hosted-checks-audit-2026-11-25.md) first. Two rules
outrank speed: the whole suite runs before anything reaches main, and nothing gets faster by hiding a failure.
No retries, no wider timeouts, no skipped tests.

- **G4 Projects.** Judgment. About 1,481 files match the root include. A read of the suite sorted them as: 577
  unit files that are clean (node, no module mocks, no globals; 59 of them read repository files and must always
  run), 297 more unit files (133 on happy-dom, 167 with module mocks), 236 that touch files, env or sqlite in
  process, 363 that spawn or listen, and 8 that need a browser. Put each file in exactly one project with a
  ratchet test.
- **G5 Leak guard and shuffle.** Judgment. The setup file compares env, globals, timers and mocks after each file
  and fails the file on a difference; files run in random order with the seed printed. Eleven `src` files change
  globals or timers and never restore them. Then write the test rules into `AGENTS.md`: ports only from
  `server/testing/ports.ts`; write only under the test's own home or temp folder and await every child; restore
  what you change in `afterEach`; read env and paths when called, not at import; an order failure is a bug, never
  a re-run.
- **G6 No isolation for the clean unit files.** Judgment. What blocks the rest: `server/config.ts` fixes
  `DATA_DIR` at first import while the setup file makes a new home per file, 116 server modules hold
  module-level state, and every file imports the message database through the setup file.
- **G7 Process tier in parallel.** Judgment. Each of those tests boots the 22,000-line server. Find the
  concurrency by measurement, starting at two files on four cores. Timeouts stay as they are.
- **G8 Split the four files over 200 s.** Mechanical for three of them (each `it` launches its own server);
  `server/index.test.ts` shares one server from an 870-line `beforeAll` that must move to `server/testing/` first.
- **G9 One definition of the whole suite.** Judgment. `merge-gate.mjs --plan` prints the steps, each hosted job
  runs `--only "<step>"`, a last job runs `--verdict` and prints `VERDICT: PASS`. Add a build step (the gate has
  none) and name platform skips as gaps. Only then does the merge rule in `AGENTS.md` change. GitHub offers no
  merge queue on a personal account, so the equivalent is this check required on a branch that is up to date.
- **G10 Selection.** Judgment. Grow `selectCiScope` in `scripts/ci-scope.mjs`. `vitest related` is not sound
  here: it misses the 228 files that start the server as a child, fake engines named by path and tests that read
  files. Everything runs on a lockfile, config, fixture, test helper, non-code file, delete or empty diff. Prove
  it with one canary per edge kind that must go red when its source is broken, and an escape audit in the gate.
  42 of the last 55 merged pull requests reach the server, so selection helps the rest.
- **G11, G12.** Every job fails over its budget; TypeScript 6 then 7 side by side (six files here and four on the
  phone import the compiler's API, among them `scripts/no-comments.ts`, and need the previous compiler kept
  beside the new one); a pre-push hook on changed files (today it takes about 85 s on four cores).

Reachable on free runners: lint and setup inside their budgets, unit shards under a minute, process shards near
two minutes. A pull request that does not reach the server should answer in 60 to 90 s; one that does, in 3 to 5
minutes, because a free account runs 20 jobs at once.

## Storage

Measured on a cloud computer: a checkout of this repository is 63 MB of files and 28 MB of shallow history, and
its `node_modules` is 1.9 GB. The phone's package store is 720 MB. So the cost of parallel work is installs, not
source: ten checkouts that each install is 19 GB.

- **On the Cloud home, never install or build.** Every dog in a home shares one machine with little free disk.
  Send installs, builds, typechecks and tests to the dog's own cloud computer with `run_on_computer`; packages
  with the same lockfile are reused across session folders there, and a saved repository environment starts ready.
- **One worktree per package, removed when its pull request is open.** The branch is on GitHub; the folder is
  not needed.
- **Outputs are disposable.** The performance script's result files belong under `.laterdog-scratch/`, which git
  ignores. The launch runner deletes its temporary folders unless `--keep` is given. The gate writes logs to a
  `laterdog-gate-*` folder in the temp directory; delete it after reading the verdict. The phone's exports under
  `.preview/` can go at any time.
- **Commit tables, not captures.** Raw data over about 100 KB stays out of the repository. Screenshots only where
  a reviewer needs to look, at double scale and small. The packages in this batch add no file over 60 KB that was
  not already there.
- **Hosted checks keep at most 10 GB of cache per repository.** One workflow writes caches, keyed on the
  lockfiles, so pull requests cannot fill it with near-copies.
- **Fresh scratch folders, never a reused name.** A cleanup that waits on a busy folder stalls the dog.

## Pace

Four packages at once, two of them on the strongest model, used up a five-hour allowance in about 35 minutes on
November 25 and stopped everything, the owner's own work included, for two and a half hours. What helped after:
at most three at once and one on the strongest setting; commit and push every working step so a stop loses
little; put long waits (a twenty-run loop, a hosted run) in a background command and end the turn; keep the
coordinating chat short, because every turn of a long chat is paid for again.
